FlytBase BDR Outbound Agent — architecture & reasoning

Input: a campaign brief (target vertical + reference account). Output: real qualified accounts, sourced decision-makers, researched context, and personalized cold emails. Every box below is running code in this repo.

The one design constraint everything else follows from: fabricated data is an automatic disqualifier. So the architecture is built to refuse to guess — an account with no source is dropped, a contact with no evidence URL is dropped, an email that can't be resolved is reported as not-found, and a thin account is sent back for more research rather than assumed either way.

1 · The execution graph is built at runtime, not fixed

The Planner does not emit a static pipeline. It starts with a single task and the graph grows as facts arrive — because how many accounts exist, and how many contacts each has, is unknowable until the search actually runs.

Planner · buildTaskGraph() Graph starts with exactly 1 task A dependency-aware executor runs it. Any task may call ctx.addTasks() mid-flight to expand the graph. No busy-polling, no fixed stage barriers — a task starts the moment its own dependencies resolve, not when a whole stage finishes.

3 · Two feedback loops

↻ Loop A — inside a run · Strategy ⇄ Research/Contacts · bounded to 1 retry

The gate scores ICP fit · evidence quality · operational pain · FlytBase mechanism relevance · contact readiness. Below threshold, it doesn't guess and doesn't reject — it emits named evidence gaps, each with an owning agent and a specific research question, and the Planner injects targeted follow-up tasks (research_strategy_gaps / search_strategy_contacts) for only the gaps that exist. Then it re-scores. Bounded to one retry on purpose: adaptation must not become an unbounded credit-spending loop.

↻ Loop B — inside a run · Writer ⇄ Critic · exactly 1 rewrite

An independent critic scores the draft against an 11-point SMYKM checklist. On failure the rewrite reuses the original writer prompt verbatim plus the specific failures, so it stays anchored to the same real facts instead of drifting to a fresh invention. If it still fails, it ships flagged rather than silently — a human sees the verdict.

↻ Loop C — across runs · machine reports, human decides

A separate analytics pass reads many past runs out of shared memory and aggregates what actually went wrong: which checklist items fail most, which evidence gaps recur, how many accounts were saved by the retry loop, why contacts went unreachable. It deliberately does not edit its own prompts or thresholds. This project twice watched a rule quietly stop being followed when it was left to the model alone; letting the system silently rewrite its own instructions is that same failure one level up. A human reads the report and changes skills/.

Loop C's very first real report immediately earned its keep: it caught the critic returning all 11 checklist items as “failures” (each labelled PASS) on emails that had actually passed — a bug invisible from any single run.

Shared memory · run_memory Agents don't pass prompts to each other Every agent writes findings to a shared, per-run key/value store and later agents read from it. Nothing is threaded through ever-growing prompt text (the old n8n pattern), so any stage can be inspected, replayed, or analysed after the fact.

Per-attempt history is kept, not overwritten — that's what makes Loop C able to ask “did the retry actually help?”

A dynamic graph makes it easy to accidentally burn a month of free-tier email credits in one run. On exhaustion the scheduler reports the skip rather than silently dropping work — a silent truncation would read as “covered everything”.
Deterministic guardrails Enforced in code, after the model em-dash stripping · suppression matching · role-fit filtering · LinkedIn profile validation · never inventing an email · forcing an empty failure list when a draft truly passed. Each of these exists because the prompt-only version was observed failing.

4 · How the problem was broken down

Sequence of reasoning 1 · Identify the hard constraint (no fabrication) before designing anything.
2 · Build the four required stages as a working system first — a running pipeline beats a diagram.
3 · Stress it against real output, and fix what actually broke rather than what looked risky.
4 · Only then add the agentic layer: a gate that can say no, a graph that can grow, a memory all agents share, and loops that close.
Where the real judgement calls were · Read FlytBase's actual case studies instead of assuming — which added a 4th decision-maker family (Digital Transformation Lead) the brief never named, and replaced logo-drops with mechanism-matched proof.
· Match proof to the prospect's own signal by mechanism, not commodity.
· Multi-thread contacts across role families so two people at one account don't get the same conversation.
· Keep Loop C human-in-the-loop on purpose.
